# How this wires in cleanly

1. **Token truth from the source**
   `DocumentChunker` now uses `offset_mapping` so every chunk has a correct `(start_char, end_char)` span even with subword pieces.

2. **Profiles tuned for NV-Embed-v2**
   Defaults remain conservative (384–512), but you can set:

   ```
   BOUNDSTATE_MAX_CHUNK=768
   BOUNDSTATE_MIN_CHUNK=128
   BOUNDSTATE_TOKENIZER_MODEL=nvidia/NV-Embed-v2
   ```

   and it will flow through `AthenaChunkingConfig` automatically.

3. **Single pass, no double-chunking**
   If the parser produces tiny lines / spans (avg < 600 chars), we concatenate text and let Athena do one token-aware pass. Otherwise we trust the parser’s structure (tables, sections) to preserve author intent.

4. **Index-friendly sections**
   `athena_adapter.chunks_to_sections` turns chunks into the exact section shape you’ve been adding: `text`, `embed_text` (title+text), `bm25_text`, stable-ish `doc_id`, `base_doc_id`, `file_name`, `section`, `title`, `source`, `tags`. That means your existing FAISS add + rerank + BM25 hybrid continues to work with zero changes.

# Sanity checks I recommend

* **Dry run on one doc with lots of tables** (e.g., a test report): confirm chunk sizes \~512–768 tokens, no mid-row splits, and `contains_table=True` appears on relevant chunks.
* **Metrics glance**: you should see `embedding_density ~ 1.0`, `chunk_coherence` jump materially (>0.5 is a good sign for prose).
* **No double saves**: make sure `smart_indexer` isn’t calling any legacy `_smart_chunk` after Athena wiring; with the patch above, it won’t.
